# 交付前检查

制作完成要求内容和结构都通过。检查过程在工作区执行，结果简述在回复中；不新增交付报告。

## 内容自检

互动交接按 interaction-tables.md 核验实际产出的两表：规则 ID 唯一、Order 唯一、所有已配置弹幕开启、每条规则有 1–8 个连续有序步骤、没有孤儿动作、每格有值或明确状态、固定类别映射真实存在。独立 Switch template 的 Switch trigger 必为 N/A；播报附加模板才有 Before/After this speech。两语言 ID、枚举、类别、顺序、数量和正式播出语言一致，提示词/条件语义同步。

双规则时具体指令在兜底回复前；单规则不自动补另一条，无规则两表零数据行。以 111、1111、hi111 和普通评论检查预期，子串与整条精确需求不一致时列为未满足/待核。分别报告静态完整性、控制台回读、预览、实播状态，禁止用前者冒充后者。可运行 `python -m unittest discover -s tests` 检查仓库合成表格样例，测试不证明生产匹配或播放。

- 每个主要段落有具体信息、情节、笑点、情绪或展示目的；没有只为凑时长的流水账。
- 人设体现在表达中，而不是每段自报身份。语气示例有情境变化，不反复套同一句。
- 不机械欢迎、感谢、反问、励志总结；普通问题直接回答，幽默符合语境。
- 承接符合已确认视频画面、音频和作用，不把观察不足写成事实。
- 互动邀请说明实际参与方式，反馈符合确认体验，频率不破坏内容节奏。
- 没有弹幕也能推进；不编造观众反应或具体点播结果。
- 设定事实、未设定事项及完整安全条款双语一致。

修正不改变提纲的内容问题可直接进行。需要改变主线、人设或互动时返回确认，而不是以“优化”名义换节目。

## 素材与互动逐项对照

在工作区逐条检查，不额外生成上传包报告：

1. 对每条固定视频，比较实际观察或用户确认的画面／音频、Introduction、播前口播和播后口播。抬爪、抬下巴、打哈欠等具体动作不互相替代。只有采样帧时不能声称已完整观看或核实音频；矛盾项回到素材核验，不能只把两份文字改成一致就算通过。
2. 对每种互动，比较邀请、有效输入、实际反馈和结束承接。只提供点播时，不暗示普通评论会获回应；若需改变互动体验，回到用户确认。无留言时仍应符合已批准的观看体验。
3. 沿正常流程追踪执行来源：需要的台词、窗口主题、故事提示和运行时状态，从哪个上传文件或已核验后台配置进入执行？仅出现在内部映射表的必需内容视为缺口。定时要求检查实际控制者，不把提示词当时钟。
4. 对每个主要口播单元，用一句话说明它新增了什么内容或体验。若多段只是重复“欢迎安静观看、你可以有自己的感受”，重写重复段，保留具体看点与角色反差；不以句式变化掩盖内容重复。
5. 对照原资料核查重要信息与角色风格的保留情况，以及双语来源／说明板块的完整性。未知曲名留待核验，不无声丢弃。

检查结果分开陈述：文件结构与行号、内容与素材一致性、执行来源、尚待平台核验。只有部分通过时明确说明缺口；文件检查不能证明实际播放可用。无法看到制作会话时，不推断用户未批准提纲。

## 跨文件主线顺序验收

分别对中英文执行：

1. 从编排索引按实际播放顺序提取固定主线口播单元，用行号工具的单元位置与索引逐项核对；按 ID 关联，不按 ID 数字排序。
2. 非循环主线的口播范围应依次向后且不重叠。行号倒退、重复引用或脚本单元遗漏均需查明原因。主线末段应为已确认的告别／收尾，不能把固定引歌放在其后。
3. 每个脚本单元都应归属于主线或明确的条件调用。条件区核对触发、返回位置及引用范围，不强求按调用次序递增。已明确的循环按一轮主线检查，并单独核对返回边；不要把合法循环或重复条件调用误报为顺序错误。
4. 调整后核对两种语言的单元序列与语义对应，分别检查各自行号、段尾下一项和索引。后台可独立选择行范围，不免除文件按主线顺序可读的要求。

完成条件：主线文本顺序与编排一致，条件／循环例外明确，所有单元有归属，受影响引用已更新。`script_index.py` 的 `OK` 仍只代表脚本结构检查通过；工具不读取编排索引，本项必须由 Agent 跨文件检查，不能宣称已由工具自动验证。

## 配置证据分层

验收摘要按四列理解：

| 证据层 | 可支持的结论 | 不能支持的结论 |
|---|---|---|
| 手册条目 | 字段名、已说明枚举、范围、保存与会话语义 | 当前场景已保存、实际媒体已播放 |
| 用户运营口述 | 本场默认、内容意图、底板观察和优先级 | 平台全局默认或未说明的枚举 |
| 样例/静态配置 | 本场编排预期、引用关系、行号和启用标记 | 实播成功、精确匹配、恢复和实际次数 |
| 上传回读/实播 | 实际 Agent/Scenario/Revision、分组保存、Brain 事件和播放结束事实 | 超出该次测试范围的全局能力 |

生成侧必须提供可查的预期：稳定 ID、媒体引用、顺序、数量、启用状态、继承/清空/设置值、双语行范围和待核字段。上传侧分别记录 Agent/Scenario 定位、各板块保存结果、冲突/部分保存、重新加载回读和实际 ID；实播另记录事件与动作。不要把一个成功的 Save 或 preview 作为另一个层级的证据。

按手册 §9、§10、§11 分别验收选评评论队列、节目互动点播窗口和弹幕规则。分别核对每次访问表演数、可接收请求数和点播期间是否计时；普通评论生成回复和指令点播也分别核对。语音情感、严格整条匹配、返场、精确代码、接收/播放次数、窗口内恢复等没有手册或实播依据时，列为待核。

- 本次正式 MD 每语言 N+5 个，一视频一模板；无新添报告、JSON、重复大小写文件。已有无关文件不计为本次新增。
- 文件名、模板 ID、类别值、视频文件、平台标识没有混用；建议映射明确标记。
- 所有纳入本场的离线视频有固定位置及前后承接；排除项已有用户确认。
- 编排顺序与段尾说明、互动映射一致，最后收尾符合确认的结束／循环要求。
- 分别计算语言版本非空行；所有口播覆盖且不含说明；存在换行变化时不沿用旧索引。
- 双语文件与板块、单元、资源关联完整；允许行数不同，数字与含义必须核对。
- 时长是一个正常区间，有依据；未知 TTS 明确是估算，不把媒体文件长度当口播上限。
- 无未解决的制作冲突被包装成“已完成”；未知平台能力只阻止依赖它的部分定稿。
- 受保护原文件／媒体未改动；复制媒体字节一致。

## 别名与底板检查

- 别名符合长度、字符和首尾规则，且项目内唯一；本地文件名通过映射表关联。
- 各互动窗口明确实际底板引用；复用资源不因前缀重复登记，独立底板类别不由前缀推断。

## 行号工具

`scripts/script_index.py` 是只读计算器。支持新规范和已见旧稿的段尾说明：

```text
[Configuration | U01 end] ...
[Configuration note | U01 end] ...
【配置说明｜U01结束】...
[配置说明 | U01结束] ...
```

每段必须有结束说明，空行不计数。重复单元、连续说明导致空段、说明后残留未归属台词、疑似说明拼写错误、混入 Markdown 元数据时返回错误并退出非零。它不验证平台是否支持、语义是否准确、每句是否自然、资源是否覆盖，也不要求中文与英文单元行数一致。

工具输出 JSON 到标准输出，供 Agent 读取并填入现有 MD 索引；不是平台导入格式，也不另存到交付目录。不得拿工具 PASS 替代内容自检或人工核验。

## 技能开发回归场景

修改本技能时用这些场景检查行为，不把测试文件加入用户上传包：

1. 只有视频和“做得有趣”：先内容访谈，不立即套数字点播。
2. “全部帮我定并生成”：询问必要约束，仍提交提纲确认后才写正式文件。
3. 已有 MIYA 角色但缺脚本：沿用角色，不套 Petopia 的世界观和时长。
4. 30 条舞蹈、10 分钟聊天目标：指出覆盖冲突，请用户选择，不暗中删素材。
5. 仅补索引但九个代码只有八条媒体：指出实质冲突并确认修复范围。
6. 用户改中文、句数变化：同步含义、单独重算双侧行号，不强制同句数。
7. 自然语言点播能力未知：先需求和核验点，不改为数字模式，不声称可上传。
8. 只改一句话：直接落盘并联动译文、索引，不重走全部访谈。
9. 同名不同媒体版本：不覆盖、不自动改名，明确选择再维护引用。
10. 模型想追加故障兜底清单：排除播放失败／超时设计；正常内容承接继续生成。
11. 互动主题或点播口播只在不上传的映射表中：识别执行来源缺口，明确上传文件或已核验配置入口。
12. 模板写抬爪而口播说打哈欠：回查素材，未观察不能判断哪边正确。
13. 原方案有两个曲名但音频未核验：保留候选曲名和待确认项，不静默删除或直接认定。
14. 三段150秒实时内容加录制歌曲：依本项目计算总长，不强行补到其他项目的20分钟。
15. 只接点播却承诺倾听反馈：对齐邀请和反馈；不未经授权增加聊天工作流。
16. 翻译正文齐全但缺来源网址，或语气示例只有独立台词：识别具体缺项，不以文件数量通过代替内容验收。

17. U01～U11 中新增第二首歌前的固定引歌 U12：插到实际播放位置，允许 U12 在 U05 前，中英文分别重算索引，告别仍为主线末段。追加到告别后、只靠索引跳转属于不合格。
18. 主线后有重复点播条件单元或节目有明确循环：核对单元归属、触发与返回边，不机械要求所有调用行号递增，不以重编号代替位置修复。
